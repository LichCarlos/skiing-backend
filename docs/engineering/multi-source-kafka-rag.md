原[项目知识组合验收](kafka-real-rag-validation.md)为 9 项。本轮在同一独立入口 `pnpm test:rag-kafka-live` 增加 8 项，实际装配 `ResortManagementModule`，验证项目知识、雪场与文章三类来源。全部业务资料均由管理 HTTP 命令创建/变更，经正式事务 Outbox、自动 polling、受限 TLS/SCRAM Kafka、consumer/Inbox、BGE-M3/pgvector 后进入 DeepSeek SSE 对话。没有替换 provider、repository、发布者或消费者，也没有直接调用 handler；调用计数 spy 仍执行正式方法。

## 新增场景

| 编号 | 验证内容                                                                                                       |
| ---- | -------------------------------------------------------------------------------------------------------------- |
| K10  | 普通用户创建文章/雪场均 403，Outbox 与审计数量保持                                                             |
| K11  | HTTP 创建两类草稿并自动消费，私有正文不调用向量模型                                                            |
| K12  | 管理端发布两类来源，自动写入真实 1024 维、L2 范数近 1 的向量，两类来源均可召回                                 |
| K13  | 两个独立登录会话分别询问合成护具规则与雪场营业时间，真实 SSE 回答带对应来源，完整消息/引用持久化一致           |
| K14  | 专用 broker 停止时编辑两类已发布内容，真实数据库仍保留旧向量，但检索立即排除；恢复 broker 后自动生成新内容向量 |
| K15  | 停止 broker 后禁用文章分类，旧文章即刻不可检索，已发布雪场仍可检索；恢复后字典事件自动消费                     |
| K16  | 分类重新启用后文章可见；再次停止 broker，文章撤回与雪场下架立即排除，恢复后两类索引停用                        |
| K17  | 两类来源软删除、最后事件/Inbox 与各五条审计核对；分类最终停用，清理合成资料及认证痕迹                          |

K13 为一个测试，包含两个独立会话/回答，结果文件分别记录。全套仍包括原 K01–K09：项目知识草稿/发布、重复事件幂等、实际 broker 进程中断、更新后回答、撤回无资料拒答和软删除。各轮执行分开计数。

本轮全局管理员编辑保持发布状态，沿用已有管理契约；商家编辑转待复审的规则不变。分类停用首先由实时 SQL 公开性过滤保证，不能误报为“字典事件自动重建了文章索引”。分类恢复仍须满足文章已发布、来源快照及其他可见性条件。本轮不修改状态流转、RBAC 或任何接口。

文章所需分类类型/项仅作 reference fixture，直接在专用空库准备；文章、雪场及项目知识正文均经正式 HTTP 管理命令写入。分类启停使用既有字典管理 API，事件由正式 worker 消费。所有问答只含虚构的服务站、雪场和护具卡资料，不向供应商发送真实用户或商家资料。

## 复现及边界

运行条件与[项目知识组合验收](kafka-real-rag-validation.md)相同：回环专用空库、显式 opt-in、安全 broker 及专用恢复 capability、真实 BGE-M3/DeepSeek 配置和仓库外输出。会实际调用模型并可能产生费用。BGE-M3 模型固定修订、1024 维与 CLS/L2 配置按[真实 RAG 说明](real-rag-validation.md)准备；本机 2048 token 配置只验证短文本。
